## 6. Ревизия кода (2026-11-06)

Проход по коду, а не по тестам: искали артефакты и тихие отказы. Найдено и исправлено:

- [x] 6.1 **Вкладка «Встречи» задваивала вхождения.** Календарь зеркалит миксин на все копии с тем же `eventId`
      (`onEventMixin`, `server-plugins/calendar-resources/src/index.ts:296`), поэтому каждое перенесённое или отменённое
      вхождение (`ReccuringInstance`) показывалось отдельной встречей. Фильтр `baseQuery={{ recurringEventId: { $exists: false } }}`
      в `Hall.svelte`. По `originalStartTime` фильтровать нельзя: его несёт и мастер серии (`makeRecurring`).
- [x] 6.2 **Напоминания могли дублироваться.** Критерий: `onClient` срабатывает повторно после повторного входа
      в той же вкладке, а `setInterval` не снимался. Сделано: один таймер на вкладку с обновляемой ссылкой на клиент
      (`meetingReminders.ts`).
- [x] 6.6 **`operator does not exist: text = text[]` на клиенте.** Запрос напоминаний использовал `$or` — адаптер БД
      воркспейса (postgres) не переводит `$or` и падает. `$or` убран, запрос снова одиночный
      (`mixin exists` + `date <= now+1ч`), лишнее отсеивает `getAllEvents`.
- [x] 6.7 **Период повторения не менялся, а дата показывала прежнее значение.** Редактор встречи
      (`EditScheduledMeeting.svelte`) подписывался на тот документ, что ему передали: если это вхождение
      (`ReccuringInstance`), правка `rules` уходила в копию, которую никто не разворачивает, а сама подписка не следила
      за мастером. Теперь редактор резолвит мастер серии (`meetingMasterQuery`, `access: owner`) и читает/пишет только его:
      `resolveMaster` + `createQuery` на мастере; `changePeriod`/`toggleReminder`/Join идут по мастеру.
- [x] 6.8 **Дата/время в форме создания применялись со второго раза.** `EventTimeEditor` (календарь) получал от
      `DateEditor` событие `update` с новым значением, но игнорировал его `detail` и пересчитывал по старому `startDate`
      — поэтому срабатывало только при следующей правке и «на предыдущее значение». Теперь `dateChange`/`dueChange`
      принимают `CustomEvent<number | Date>` и ставят значение из `detail` (число или `Date`).
- [x] 6.9 **В «Постоянных встречах» не было удаления.** У таблицы есть селекция, а действия удаления для
      `PermanentMeeting` не было: стандартный `view.action.Delete` закрыт проверкой прав, которую Space не проходит.
      Добавлен override `view.action.Delete` с `visibilityTester: view.function.CanDeleteSpace`, категория Office, режимы
      `context` + `browser`; живые сессии удалённой встречи завершает серверный триггер (6.5/4.4). Дата/время у
      постоянной встречи не бывает по модели — она открыта всегда; редактируемы имя и период `repeatEvery` в панели.
- [x] 6.3 **`RepeatEveryEditor` молчал в панели свойств.** Модель регистрирует его как атрибутный редактор
      (`editor: love.component.RepeatEveryEditor`), а атрибутному редактору `onChange` не передаётся: правка числа ничего
      не сохраняла. Теперь без `onChange` редактор пишет сам (`client.diffUpdate` по переданному `object`).
- [x] 6.4 **`MeetingData` не читал флаг из состояния.** `isMeeting` всегда начинался с `false`, хотя `$state`
      мог уже содержать включённый флаг (повторное открытие формы). Теперь `$state.isMeeting === true`.
- [x] 6.5 **Сборка `pod-love` падала на Windows.** `bundle:template` (`services/love/package.json`) опять
      копировал `index.html` через `fs.cpSync`, а тот на Windows отдаёт `errno 0` / «The operation completed
      successfully» на `unlink` занятого файла — и валит всю цепочку `pnpm docker`. Подключён уже лежащий
      в репозитории помощник `common/scripts/copy-file.js` (повторная поопытная копия вместо unlink). Проверка:
      `pnpm run bundle:template` два раза подряд + `pnpm docker:build --to @hcengineering/pod-love`.
