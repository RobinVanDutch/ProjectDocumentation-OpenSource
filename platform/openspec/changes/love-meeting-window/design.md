# Design: окно встречи по макету

## 1. Две карточки вместо одной

| Что открывается                                 | Компонент                        | Заголовок           | Состав                                                                               |
| ----------------------------------------------- | -------------------------------- | ------------------- | ------------------------------------------------------------------------------------ |
| Встреча (событие с миксином `MeetingEventLink`) | `EditMeeting` (love-resources)   | «Настройки встречи» | О встрече / Когда / Где / Участники / Напоминания                                    |
| Обычное событие календаря                       | `EditEvent` (calendar-resources) | «Событие»           | Название, Описание, Когда, Где (место, календарь, видимость), Участники, Напоминания |

Причина: набор полей разный по смыслу. «Местоположение» — свободный текст события; у встречи вместо
него комната (`MeetingEventLink.room`). «Видимость» — свойство события в календаре; у встречи роль
играет тип (разовая/повторяющаяся), группа и `private`. Одна карточка с ветвлениями уже была —
владелец её отверг.

## 2. Как окно открывается

`calendar-resources` уже имел `eventCard(client, event, calendarEditor)` и таблицу резолверов, но клики
по событию её не использовали (вызывали `showPopup(EditEvent)` напрямую). Добавлено:

- `EventCardResolver` может вернуть либо документ (панель документа), либо `EventCardWithEditor`
  `{ object, editor }` — «это событие, и окно у него вот такое»;
- `openEventCard(client, event, calendarEditor)` — единая точка: резолвер → панель документа →
  `EditEvent`, если никто событие не забрал;
- `EventElement.svelte` и `Day.svelte` вызывают `openEventCard` вместо `showPopup`.

Любовь регистрирует резолвер: `findMeetingLink` нашёл миксин → `{ object: серия, editor: EditMeeting }`.
Остальные резолверы и миксин-поиск `eventCard` не менялись, поэтому событие без встречи ведёт себя как
раньше.

## 3. Серия, а не вхождение

Клик приходит по вхождению (`calendar.class.ReccuringInstance`). Запись в него не видна: календарь и
список читают серию. Мастер ищется ровно так, как это делает `updateReccuringInstance` в
`calendar-resources/src/utils.ts`:

```ts
const found = await client.findOne(calendar.class.ReccuringEvent, {
    calendar: event.calendar,
    eventId: instance.recurringEventId,
});
```

Проверено на стенде: до правки поле имени не сохранялось (в логе `class: calendar:class:ReccuringInstance`,
`update sent { title }`, список без изменений); после — имя меняется в списке и возвращается обратно.
Поиск по `_id: recurringEventId` **не работает**: `recurringEventId` — это `eventId` мастера, не его `_id`.

## 4. Поля окна встречи

- **О встрече**: Название (`TextInput`, `autofocus`), Описание (`TextArea`, `rows={2}`, `maxRows={5}` —
  вместо tiptap-редактора), Группа (`Dropdown` по `love.class.MeetingGroup`; строка скрыта, если групп
  нет), Тип (значение: «Разовая встреча» / «Регулярная встреча» по наличию `PermanentMeeting`).
- **Когда**: Весь день (`Toggle` + подсказка-иконка `hint`), Дата (два `DateSelect`, `stacked`),
  Часовой пояс (`Button hasMenu`), Повторять каждые (`NumberInput` + `Dropdown` единиц, только у
  повторяющейся) с подписью «Следующая встреча: …» в `setting-row__details`.
- **Где**: Переговорная (`Dropdown` по комнатам офиса, `placeholder` — «Комната»), Отображение в
  календаре (`Toggle`, только у повторяющейся, пишется в `PermanentMeeting.calendar`).
- **Участники**: `EventParticipants` + `EventRsvp` (см. §6).
- **Напоминания**: «Напоминать» (`Toggle`), «Время напоминания» (`MenuButton` с `multiselect`) и чипы
  выбранных задержек, «Нет напоминаний» когда выключено.

Разметка и стили повторяют макет 1:1: `.meeting`, `__summary`, `__field` (12rem, `--wide`, `--zone`,
`--auto`, `--unit`), `__control`, `__range`, `__dash`, `__value`, `__note`.

## 5. Подписи и локали

- Общие подписи календаря объявлены в `models/calendar/src/plugin.ts` (модель — дом для того, что нужно
  нескольким плагинам): `About`, `When`, `Where`, `Remember`, `Reminder`, `ReminderTime`, `AddReminder`,
  `NoReminders`, `AllDay`, `TimeZone`.
- Строки встречи — `plugins/love-resources/src/plugin.ts`: `MeetingType`, `RepeatDays`, `RepeatWeeks`,
  `RepeatMonths`, `AllDayHint`; `RecurringMeeting` и `OneOffMeeting` уже существовали и переиспользованы.
- Переводы добавлены во все 12 локалей каждого пакета (`calendar-assets`, `love-assets`).
- В `love-resources` строки видны только если объявлены в его собственном `string`-наборе: `mergeIds`
  сливает строки, но набор плагина — то, что реально читает компонент (иначе в разметке `undefined`).

## 6. Открытые решения

1. **Участники.** В макете — `MenuButton` (иконка «добавить людей») + чипы; в проде — `EventParticipants`
   с поиском, аватарами, занятостью (`ParticipantsBusy`), RSVP и гостями по почте. Для паритета с макетом
   нужно переписать пикер и сохранить гостей по email — отдельная работа, решение за владельцем.
2. **«Доступ по ссылке».** В макете секция с «кто может начать», паролем, ссылкой, TTL и поведением
   после последней встречи. Сейчас это `MeetingLinkPopup` из `EditMeetingData`; перенос в окно —
   следующий шаг, если нужен.
3. **«Удалить» в футере.** Макет показывает `negative-ghost` «Удалить» слева для владельца; в окне пока
   только «Отменить / Сохранить». Удаление встречи — существующие действия, перенос не делали.
4. **`EditMeetingData` как расширение `EditEvent`.** Раз встречи идут в своё окно, блок «Встреча /
   Переговорная / Ссылка» внутри `EditEvent` больше не показывается. Проверить, не стал ли компонент
   мёртвым кодом, и либо оставить для календарных событий со ссылкой, либо удалить.
5. **Светлая тема и узкие экраны** окна встречи отдельно не проверялись.

## 7. Ответы участников: где живут и как рисуются (2026-11-26)

**Где живёт ответ.** Свой ответ участник пишет в `Event.rsvp` — в СВОЮ копию события, которая лежит
в его личном пространстве. Организатор держит мастер. Ни один клиент не может прочитать все копии,
поэтому серверный триггер собирает ответы и раскладывает их обратно:

| Поле | Кто пишет | Кто читает |
| --- | --- | --- |
| `Event.rsvp` | участник в свою копию | он сам (его ответ в футере карточки) |
| `Event.rsvpSummary` (`accepted/declined/tentative`: числа) | серверный триггер `rsvpSummaryTxes` | все, у кого есть копия |
| `Event.rsvpMembers` (`Ref<Person>[]` по состояниям) | он же | все, у кого есть копия |

Агрегат раскладывается **в каждую копию**, а не только в мастер: иначе приглашённый видел бы только
свой ответ. `user` копии — это social id, персона находится через `contact.class.SocialIdentity`, и в
документ пишется именно `Ref<Person>` — так карточке не приходится самой разбирать social id.

**Почему не «по одному запросу на карточку».** Клиент не может прочитать копии других участников ни
запросом, ни правами — раскладка по копиям это единственный вариант без нового серверного эндпоинта.
Цена: `N` записей на один ответ (по числу копий). Неизменённые документы не переписываются — сравнение
отсортированных списков.

**UI.** Один компонент `MeetingRsvpSummary.svelte` на две карточки:

- `expandable={false}` в окне настроек — только строка счётчиков, полным списком имён остаются чипы
  участников ниже (им же нужны кнопки «Убрать»);
- по умолчанию в карточке приглашённого — строка счётчиков, клик раскрывает группы с именами; имя —
  кнопка в профиль, гости — отдельной строкой с `@`.

Счётчики — ICU-плюралы (`RsvpAcceptedCount` и т.д.), а не склейка числа с подписью: «1 придёт» против
«4 придут» в русском не склеивается. Старые встречи, где имён ещё нет, показывают счётчики из
`rsvpSummary` и честно не называют имена.

**Свойство, которое сломалось и восстановлено.** «Встреча — это событие с миксином `MeetingEventLink`»
должно читаться по данным документа. Фолбэк `findMeetingLink`, возвращавший сам документ события,
делал встречей любое событие, а выдача гостевой ссылки (`updateMixin({ linkId })`) довершала это,
создавая миксин. Отсюда правило: поиск ссылки не возвращает документ, который не несёт миксин, а
`updateMixin` нельзя вызывать как «создать миксин, если его нет» на пути выдачи ссылки.
