# Design

## Context

PR #428 принёс новую модель: мастер-событие календаря с миксином `MeetingEventLink` — «серия»,
`MeetingMinutes` — сессия вхождения, `PermanentMeeting` — постоянная встреча без расписания.
Сессию создаёт `resolveSession` по входу, статуса `Scheduled` нет, отзыв ссылки — бамп `linkVersion`,
права гостя — `meetingAccess` (`start: 'members' | 'link'`, `past`, `afterTtl`, `guestPassword`).

Наш прежний change `love-meeting-link` (`startOnLink`, `restartMeeting`, перезапуск `Scheduled`) слиянием
поглощён: этих полей в модели PR нет. Остались живыми только две наши правки — валидация имени гостя
и стабильный `guest-link:<sha256>`.

## Goals

- Закрыть P1 из `audit-pr-428.md` §8: перенос вхождения, владелец постоянной встречи, режимы гостя.
- Довести P2: путь навигатора, мёртвые поля модели, дефекты UI из §7.
- Зафиксировать в требованиях то, что PR уже делает (пароль, rate limit, авторизация API, RSVP).

## Non-Goals

- **Перенос вхождения серии** — перенесён на следующую итерацию (решение 2026-11-03): источник override не согласован,
  без него не обойтись, а остаток работ от него не зависит. Задачи группы 2 остаются в `tasks.md` как отложенные.
- Внеплановый старт по ссылке (этап 5 плана): решение не принято, PR показал другую семантику (§11.1).
- Особые права владельца воркспейса на ссылку: ссылку выдаёт участник, остальные подписываются (`authorizeTarget`);
  логики «владелец воркспейса меняет ссылку запланированной встречи» не восстанавливаем.
- Переделка механики ссылок PR (payload-указатель, `linkVersion`) — она принята как есть.
- RSVP: расширение поведения; здесь только описание и один фикс `pending`.

## Decisions

1. **Перенос вхождения — отложен.** Решение от 2026-11-03: уходит в следующую итерацию. Прежний выбор (override из `PersonSpace`) не отменён, но не согласован с владельцем репозитория; пока группы 2 нет в работе, спека не требует от кода того, чего он не делает — требование живёт в этом change без реализации.
2. **Владелец постоянной встречи.** Два уровня, оба обязательны:
   - сервер — триггер `OnPermanentMeetingUpdate` (`server-plugins/love-resources`): правка `members` без владельца
     исправляется обратной правкой (`$push` отсутствующих `owners`) с логом. Отклонить транзакцию триггер не может,
     поэтому инвариант держится ответной правкой; зацикливания нет, потому что транзакция исправления несёт `$push`,
     а не `members`;
   - клиент — свой редактор `PermanentMeetingMembersEditor` (`plugins/love-resources`), поставленный
     `createAttributePresenter` на `love.class.PermanentMeeting, 'members', 'array'`: владельцы идут в
     `protectedAccounts` (снять нельзя), само поле доступно только владельцу. Общий `SpaceMembersEditor`
     из `contact-resources` не тронут — он обслуживает все `Space` (каналы, воронки), и чтобы он знал про `owners`,
     пришлось бы менять `MembersBox` и панели чужих плагинов.
3. **Режимы гостя.** `/guestInfo` для `kind === 'meeting'` не отдаёт `after`: сессия постоянной встречи
   завершается, но сама встреча — нет, поэтому «после» для неё бессмысленно.
4. **`linkId` (пересмотрено 2026-11-03).** Концепция PR сохраняется: поле остаётся в модели (`MeetingEventLink` с индексом, `PermanentMeeting`) и в типах. Расхождение «объявлено — не пишется» закрывается записью shortId при выдаче ссылки (`GET /meetingLink`), а не удалением поля. `TMeetingSchedule.meetingId` тоже остаётся как в PR; связь сессии с серией всё равно идёт через `eventId`/`meeting`.
5. **Пароль и rate limit** описываются как есть (`pbkdf2-sha256`, 100 000 итераций, 10 промахов / 15 минут
   на «ссылка + IP»), без изменения поведения.
6. **Права владельца workspace** (решение 2026-11-03): на ссылку — нет никаких, ссылку выдаёт участник и остальные
   по ней подписываются. При этом уже существующие обходы роли `Owner` в доступе к приватной встрече
   (`/getToken`, `joinMeeting`, `/kickParticipant`) **сохраняются**: это поведение продукта, а не часть механики ссылок.
7. **Внеплановый старт по ссылке — не реализуем** (решение 2026-11-03). Альтернативой был `start: 'link'` плюс сессия
   с `occurrence = null` вне окна; отклонено, потому что окно вхождения защищает приватность ссылки на серию,
   а сессия без вхождения разъезжается с календарём и ломает инвариант «одна живая сессия на вхождение».
   Потребность «созвониться в любой момент» закрывает `PermanentMeeting`.
8. **Файлы, разрешённые при слиянии PR #428, — авторские** (решение 2026-11-03). Их не переписываем и не
   рефакторим ради тестируемости: `authorizeTarget` остаётся в `main.ts` (вынос в `linkAuth.ts` откачен),
   фильтр организатора остаётся в `EventRsvp.svelte` (хелпер `rsvpInvitedCount` откачен), ссылки на картинки и
   формулировка `meetingAccess.start` в `docs/love.md` — как в слиянии. Правки этих файлов — только аддитивные
   и только после согласования.

## Risks

| Риск | Как снимаем |
|---|---|
| Ответная правка `members` ломает штатное сохранение | Правим только отсутствие владельца в новом наборе, остальные правки проходят |
| Запись `linkId` из сервиса добавляет транзакцию на каждую выдачу ссылки | Пишем только когда shortId отличается от текущего; для серии — `updateMixin` мастера |
| Ошибка в `navigateToOfficeDoc` ломает переходы из звонка | Проверяется сценарием «в звонке → протокол → назад», а не только статической навигацией |

## Migration Plan

1. Порядок: сначала требования и документация (текущее состояние кода), затем P1 (перенос, владелец, режимы),
   затем P2 (навигатор, модель), затем P3 (тесты и docs).
2. Удаление полей модели не делаем — модель остаётся как в PR (решение 2026-11-03).
3. После приёмки `love-meeting-link` закрывается как поглощённый PR, `love-meetings-pr428-gaps` архивируется
   в `openspec/specs/`.

## Open Questions

1. Перенос вхождения: читать override из `PersonSpace` или договориться, что перенос пишет `rdate`/`exdate`
   в мастер (§11.2). Вопрос ждёт следующей итерации.
2. Что делать с `room`/`meetingId` в миксине `MeetingEventLink`, объявленными legacy: удалять отдельным change
   или оставить до следующего мажора (в этой итерации — оставляем).
