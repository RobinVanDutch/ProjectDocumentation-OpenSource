# Design

## Context

Состояние кода на 2026-11-06 (ветка `FUSIO-1307-livekit-shared-link`, HEAD `e2da22dca2` + правки этой сессии).

- **`PermanentMeeting extends Space`**: `type`, `language`, `startWithRecording/Transcription`, `repeatEvery` (мс),
  `linkId`, `linkVersion`, `meetingAccess`, `members`, `owners`. Расписания нет — считается «открыта всегда».
- **Серия события** (`calendar.class.ReccuringEvent`) с миксином `MeetingEventLink` на мастере несёт `rules`,
  `reminderBefore`, `meetingAccess`, `linkId`, а `MeetingEventLink.permanentMeeting` связывает её с постоянной
  встречей. Сессии (`MeetingMinutes`) открывает `resolveSession` по `eventId` + `occurrence`.
- **`CreatePermanentMeetingPopup`** создаёт только `PermanentMeeting` (название/тип/запись/транскрипция/участники).
- **Таблица** `love.viewlet.TablePermanentMeetings`: колонки «название (презентер)», `members`, `createdOn`;
  действий в строке нет. Селекция есть (штатная у Table), применять некуда.
- **Гостевая ссылка**: `getEventMeetingLink(id, 'meeting')` для постоянной встречи, `copyGuestLink` — для сессии;
  `MeetingLinkPopup` правит политику и пароль (`loveClient.setGuestPassword(ptr, pwd, 'meeting')`).
- **Права сейчас**: `view.action.Delete` зарегистрирован с `CanDeleteSpace`; `LeavePermanentMeeting` с
  `CanLeavePermanentMeeting` (создателю запрещено, участнику можно), серверный `OnPermanentMeetingUpdate`
  возвращает владельца в `members` и завершает сессии при удалении.
- **Готовые паттерны**: DnD с маркерами — `DropArea.svelte`/`DropMarker` (`controlled-documents-resources`,
  `DocHierarchy`), список с группами и перетаскиванием — `ToDoDraggable.svelte` + `dragging` (`time-resources`);
  строковые действия в таблице — `SharingStateIndicator`/`RoomTablePresenter`; модалки — `Card`.

## Decisions

1. **«Постоянная встреча» = расписание + комната.** Модалка создаёт **два** документа: серию (`ReccuringEvent`
   с `rules` из выбранной регулярности, дата/время — начало серии) и `PermanentMeeting`, связанную через
   `MeetingEventLink.permanentMeeting`. Причина: вхождения, окно входа, `occurrence`, гостевой лобби и завершение
   сессий уже работают по серии; вторая реализация расписания на `PermanentMeeting` дублировала бы календарь и
   не давала бы вхождений. Альтернатива (b) «поля даты прямо в `PermanentMeeting`» отклонена.
2. **Регулярность — календарные `rules`.** Дату/время и периодичность задаём тем же `RecurringRule`, что и в
   календаре (`PERIODICITY`: день/неделя/месяц + интервал + окончание). Для формы — компактный редактор
   (`RepeatEveryEditor` + единица), конвертация в правило уже есть (`periodRules`/`ruleToPeriod` в `period.ts`).
3. **Напоминание** — `MeetingEventLink.reminderBefore` (мс) на мастере серии; для встречи без серии — новое
   поле `PermanentMeeting.reminderBefore`. Значение по умолчанию 15 минут, `0` — выключено.
4. **Пароль гостей** — существующий механизм: `meetingAccess.guestPassword` пишет только сервис love через
   `POST /meetingPassword`; модалка вызывает `setGuestPassword(pointer, pwd, 'meeting')` и не читает хеш.
5. **Гостевая ссылка** — `linkId` на связи (серия или постоянная встреча). После создания показываем блок с
   готовой ссылкой и кнопкой «Копировать»; в строке таблицы — действие `CopyGuestLink`.
6. **Группы.** Новый класс `MeetingGroup` (`name`, `order`) + у встречи `group: Ref<MeetingGroup>` и
   `order: number`. Объединение выделенных создаёт группу и проставляет её встречам; DnD меняет `order` группы
   и `order` встречи (внутри группы). Переиспользуем `DropArea`-маркеры (как в `DocHierarchy`), без нового DnD-движка.
7. **Права.** «Создатель» = `createdBy` документа либо единственный `owners[0]` для старых данных; удалять может
   только он (visibilityTester + серверный guard), остальным доступно только «Покинуть». Создателю «Покинуть»
   скрыто (уже реализовано в `CanLeavePermanentMeeting`), но серверная проверка в `OnPermanentMeetingUpdate`
   дополнительно не даёт снять создателя из `owners`.
8. **Режимы правки вхождения** — «Текущая» и «Все (будущие)». `UpdateRecInstancePopup` для встреч показывает
   только эти два варианта (режим «next» маппится в «все будущие»).
9. **Все изменения кода фиксируются в этой спеке** (правило spec-first): задачи в `tasks.md` отмечаются по мере
   реализации, расхождения с планом сначала попадают сюда.

## Risks

| Риск | Как снимаем |
|---|---|
| Два документа на одно действие (серия + встреча) расходятся при правке | Все правки идут через мастер серии и `permanentMeeting`; название синхронизируется существующим `EditPermanentMeeting`/триггером |
| Удаление встречи оставляет серию и сессии | Серверный триггер завершает сессии (есть); удаление серии — той же транзакцией из клиента |
| Группы ломают сортировку таблицы | `order` — явное поле; сортировка по умолчанию — `order`, остальные сортировки временные |
| Права обходятся прямым вызовом клиента | Проверка и в `visibilityTester`, и на сервере (триггер/мидлварь) |
| Миграция не догоняет старые воркспейсы | Новые модельные документы (действия, группа) — шагом миграции, как у бейджа/триггера |

## Open Questions (закрыты 2026-11-06 ответами владельца)

1. **Расписание обязательно — да.** Владелец: постоянная встреча всегда открыта, «но мы это делаем, чтобы в
   расписании показывало, что встреча». Поэтому дата/время обязательны: серия даёт вхождения в календаре, а
   `PermanentMeeting` — всегда открытую комнату. Регулярность необязательна (без неё — одно вхождение + комната).
2. **Группы плоские — да.** Вложенных групп нет, встречи перетаскиваются между группами и внутри.
3. **Создатель у старых данных** — `createdBy`, при его отсутствии `owners[0]`. Подтверждено.
4. **Пароль для гостей** — только установка/снятие, текущий хеш наружу не отдаётся. Подтверждено.
