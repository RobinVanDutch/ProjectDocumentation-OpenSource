# Design

> Перед чтением — блок «ПРОЧИТАТЬ СРАЗУ ЖЕ ПЕРЕД ВЫПОЛНЕНИЕМ» в `proposal.md`. Здесь только техническая часть:
> первопричины с доказательствами и выбранные решения.

## Контекст: как устроена ссылка

- Гостевая ссылка — `shortId` от payload `buildMeetingLinkPayload({ eventId, workspace, linkVersion, kind })`
  (`plugins/love/src/utils.ts:474-510`, `services/love/src/guests.ts:325-335`). Один и тот же payload даёт один и
  тот же shortId; **единственный способ сделать ссылку другой — увеличить `linkVersion`**.
- `linkVersion` живёт: у события — в миксине `love.mixin.MeetingEventLink` мастера, у постоянной встречи — в
  документе `love.class.PermanentMeeting`.
- Проверка «ссылка ещё жива» — `checkMeetingLink(link, claimed, { nextOccurrence | lastMeetingEnd }, now)`:
  несовпадение версий → `revoked`, отсутствие будущего вхождения и истёкший `afterTtl` → `expired`.
- Сейчас `linkVersion` увеличивают только ручные действия: `revokeMeetingLink` / `revokePermanentMeetingLink`
  (`plugins/love-resources/src/utils.ts:410-424`). Ни один триггер `linkVersion` не пишет (grep по
  `server-plugins/**` пуст).

## Decision 1. Перенос времени: ссылка та же, встреча пересоздаётся по новому слоту

> **Уточнение владельца 2026-11-13 (отменяет прежнее решение о перевыпуске).** Дословно: «есть пункт с созданием
> новой ссылки, этот пункт убрать и сделать чтобы менять не ссылку, а в базе двигать время начала и пересоздавать
> встречу по той же ссылке если её перенесли». Значит: `linkVersion`/`linkId` при переносе НЕ меняются,
> перевыпуска ссылки нет; время пишется в документ, а встреча (сессия) пересоздаётся под той же ссылкой.

**Почему ссылка может остаться той же.** Гостевой shortId — это `shortId` от payload
`{ eventId, workspace, linkVersion, kind }` (`plugins/love/src/utils.ts:474-510`, `services/love/src/guests.ts:325-335`).
Времени в payload нет: одно и то же событие с той же версией всегда даёт один и тот же адрес. Время влияет только
на то, какое вхождение сейчас «открыто», и это считается на входе (`resolveSession` → `resolveOccurrence` по
мастеру + исключениям серии). То есть перевыпуск ссылки при переносе был технически лишним и, как сказал владелец,
вредным: люди продолжают пользоваться присланной ссылкой.

**Что реально ломается сейчас (доказательства по коду).**

1. `resolveSession` (`services/love/src/workspaceClient.ts:817-834`) ищет живую сессию запросом
   `{ eventId, status: { $in: LIVE_MEETING_STATUSES } }` и **не сверяет её `occurrence` с текущим вхождением**.
   Сессия, созданная для прежнего слота, после переноса продолжает возвращаться: у неё `occurrence` = старый старт,
   `roomId`/metadata — от старого слота, статус `Pending`. Внешне это «встреча не открывается в новое время».
2. Исключения серии читаются запросом с `$or` (`workspaceClient.ts:784`), который Postgres-адаптер не переводит
   (`operator does not exist: text = text[]`) — поэтому перенесённое вхождение вообще не находится и даёт
   `no-occurrence` → `403 {"error":"Meeting is not open"}`. Это отдельный дефект, Decision 2.

**Решение.**

1. Время пишет редактор в документ: у одиночного события и мастера серии — `date`/`dueDate`, у серии с повторением
   — `rules`/`rdate`/`exdate`, у постоянной встречи — поля расписания плюс мастер серии. Никаких триггеров на
   `linkVersion`, никакого перевыпуска и никакого текста «ссылка перевыпущена» (пункт снят).
2. Идентичность вхождения — новый чистый помощник `occurrencePin(current, overrides)` в `plugins/love/src/utils.ts`:
   для перенесённого вхождения это `originalStartTime` (так уже документировано в `MeetingMinutes.occurrence`,
   `plugins/love/src/types.ts:260-262`), для обычного — сам старт. Помощник нужен, чтобы сравнивать пин сессии
   с текущим слотом в одном месте и не разъезжаться с `meetingOccurrences`.
3. `resolveSession` принимает живую сессию только при совпадении пина: `live.occurrence === occurrencePin(...)`.
   Не совпало и сессия в `Pending` — она завершается (`finishMeeting(live._id, now)`) и создаётся новая с той же
   `eventId` и новым `occurrence`. Ограничение `notMatch` (одна живая сессия на встречу) не меняется.
4. `Active` завершается так же: решение владельца 2026-11-13 — «завершить и пересоздать по новому времени»,
   то есть перенос во время звонка прерывает звонок (участники выходят, следующий вход открывает новый слот).
   Условие одно и то же — расхождение `occurrence` живой сессии с пином текущего вхождения.
5. LiveKit-комната (`ensureRoom`) не пересоздаётся: она адресуется именем `${workspace}_${meetingId}` и
   переиспользуется; пересоздаётся именно сессия (`MeetingMinutes`), которая несёт `occurrence` и слот.

**Инварианты.**

- `linkVersion` и `linkId` не зависят от времени. Единственный их писатель — явный отзыв в UI
  (`revokeMeetingLink`/`revokePermanentMeetingLink`, `plugins/love-resources/src/utils.ts:410-424`).
- `MeetingMinutes.occurrence` = пин вхождения (для перенесённого — исходный старт). История сессий остаётся
  привязанной к исходной точке серии.
- Перенос одного вхождения не пересоздаёт сессию: у неё `occurrence` = `originalStartTime`, пин после переноса
  считается тем же, а время показа берётся из `resolveOccurrence`.

**Проверка.** Unit: `occurrencePin` (обычное вхождение, перенесённое, отсутствие вхождения); `resolveSession`
(сессия прежнего слота → `Finished` + новая с заданным `occurrence`; совпадающий пин → та же сессия; `Active` →
`Finished` и новая). Сквозная (Playwright + база): создать встречу → получить ссылку → перенести на час → испросить
ссылку снова (тот же shortId) → войти по старой ссылке → в БД `event.date` новое, новая `MeetingMinutes.occurrence`
равна новому времени, прежняя сессия `Finished`.

## Decision 2. 403: `$or` в запросе исключений серии и обработка отказа на клиенте

**Первопричина (доказано логом).** `occurrenceOverrides` читает `calendar.class.ReccuringInstance` запросом
`{ recurringEventId, $or: [{ date: { $gte } }, { originalStartTime: { $gte } }] }`
(`services/love/src/workspaceClient.ts:778-796`). Postgres-адаптер не поддерживает `$or` и превращает его в
сравнение колонки:

```
event.data#>>'{$or}' = ARRAY['[object Object]','[object Object]']::text[]
→ PostgresError 42883: operator does not exist: text = text[]
```

Результат: исключения не читаются вообще, `resolveOccurrence` считает вхождения по расписанию мастера, перенесённое
вхождение в свой слот отсутствует → `no-occurrence` → `403 {"error":"Meeting is not open", nextOccurrence}`.

**Решение.**

1. Запрос без `$or`: `client.findAll(calendar.class.ReccuringInstance, { recurringEventId })` и фильтрация по
   `now - SCHEDULED_MEETING_WINDOW_MS` в памяти. Вхождения одной серии — единицы; выигрыш от SQL-фильтра здесь не
   стоит поддерживаемости. Вариант «два запроса и слияние по `_id`» допустим, но второй запрос по
   `originalStartTime` сравнивает текст (`data#>>`), то есть сортирует лексикографически — не полагаться на него.
2. Ошибка чтения исключений больше не маскируется: `catch` остаётся (серия без исключений лучше, чем отказ входа),
   но логируется как `error`, а не `warn`, и не должна появляться на штатных запросах — критерий в задачах.
3. Клиент обрабатывает отказ резолва как штатный результат: `joinMeetingBySession`
   (`plugins/love-resources/src/meetings.ts:246`) ловит `LoveServiceError` со `status === 403` и показывает
   текстовый статус (`love.string.MeetingNotOpenNow` / «Ещё не началось, ближайшее вхождение — …»), **не** бросая
   ошибку вверх: в dev-сборке текущий вылет даёт красный оверлей «Uncaught runtime errors», в прод-сборке —
   молчащую кнопку.

**Воспроизведение на стенде (2026-11-12).** Клик по значку камеры на прошедшем событии даёт
`LoveServiceError: resolveSession failed: 403 {"error":"Meeting is not open"}` из
`MeetingEventBadge.join` → оверлей webpack-dev-server. Это и есть пункт 3 владельца.

## Decision 3. Откат отображения: эталон — `git HEAD`, а не «как кажется красивее»

**Правило.** Для файлов из списка ниже эталон — состояние в `git HEAD` (то есть до правок этой ветки). Правки
вида, сделанные поверх, откатываются целиком, кроме случаев, явно перечисленных в задачах.

| Файл                                                                 | Что откатывается                                                                                                                                                                                                                                                                                       |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `plugins/love-resources/src/components/PermanentMeetingsList.svelte` | клик по строке снова открывает `openSettings`, а не `openDoc`; удаляются шестерёнка, обёртка `.actions` и её стили; восстанавливаются кнопки «копировать/вступить/удалить или покинуть» и `.count` в заголовке группы; `gap-1` → `flex-gap-1` остаётся (это исправление выравнивания иконок, а не вид) |
| `plugins/love-resources/src/components/EditScheduledMeeting.svelte`  | кнопка «Join meeting» возвращается к прежнему обработчику (`joinMeetingBySession(live.eventId, 'event')`), если не подтверждено обратное на стенде; `joinLive` убирается                                                                                                                               |
| `plugins/love-resources/src/components/MeetingEventBadge.svelte`     | остаётся только добавление различия «постоянная/обычная», реализованное на существующей разметке и стилях; собственные стили `.permanent-mark` сводятся к минимуму либо заменяются существующим токеном/компонентом                                                                                    |

**Почему так.** Владелец сформулировал требование как «верни как было», а не «сделай лучше»: любая новая
интерпретация снова окажется «дресней». Различия фиксируются по `git diff HEAD -- <файл>`.

## Decision 4. Тестовое покрытие: две матрицы, не «по файлам»

**Слой A — компонентные тесты (vitest + jsdom, рядом с компонентом).** Дёшево, быстро, без стенда:
рендер строки списка встреч и её действий по правам, текст «ссылка скопирована», пароль гостя, сообщение об
отозванной ссылке, значок постоянной встречи, попап перехвата комнаты, панель группы.

**Слой B — Playwright-sanity (`tests/sanity/tests/love/**`, `tests/sanity/tests/calendar/**`).** Сквозные пути,
которые нельзя проверить в jsdom: создание встречи с комнатой из планировщика и из вкладки «Встречи», старт
встречи (сессия в выбранной комнате), перехват занятой комнаты (второй участник), копирование ссылки,
гостевой вход с паролем и по отозванной ссылке, объединение в группу, перенос встречи и перевыпуск ссылки,
вход на прошедшую встречу (текст вместо оверлея).

**Обязательный минимум (список в `tasks.md`)** покрывает каждый пункт, сделанный 2026-11-09 … 12: комнаты в
форме создания, `rules: []` (простое событие не считается серией), текст копирования, пароль гостя,
отозванная ссылка, выравнивание иконок в списке, группы, значки в планировщике, перехват комнаты.

## Открытые вопросы (решить в начале выполнения)

1. **Какой именно экран назван «отображением запланированной встречи»** — строка списка «Постоянные встречи»,
   карточка `EditScheduledMeeting` или плитка в календаре «Встречи». Решение по умолчанию: откатить **все три**
   к `git HEAD` (это безопасно и точно соответствует формулировке «верни как было»), затем, если владелец имел в
   виду только один, лишний откат убрать.
2. **Нужно ли показывать пользователю, что ссылка перевыпущена.** По умолчанию — да, коротким текстом в
   статус-баре (тот же механизм, что «Ссылка скопирована»); пункт помечен как «уточнить», на требование о
   перевыпуске не влияет.
3. **Перенос вхождения серии**: ссылка не меняется (серия та же), проверяется сценарием «гость входит по
   перенесённому времени». Если владелец ждёт перевыпуск и здесь — это отдельное правило, ломающее TTL ссылки
   серии; без его подтверждения не реализуем.
